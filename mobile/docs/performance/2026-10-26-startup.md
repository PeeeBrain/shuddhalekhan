# iPhone startup and transcription measurements

## Target and method

Reduce each measured latency by at least one third against the same-device baseline. Compare process-cold starts separately from repeated sessions in the same process. First-time model installation, permission prompts, and prepared Core ML caches are separate cases.

The maintainer later clarified that transcription/inference was never the bottleneck. The remaining priorities are new-session startup and custom keyboard responsiveness, including the dictation panel wobbling on opening and missing pressed-key feedback. Further inference tuning was stopped. Builds were held while the maintainer was away; they subsequently authorized build 6, with device testing deferred until available.

Measure session request to usable session, first and repeated transcription, and keyboard Stop to insertion. Use the same spoken test sentence and comparable recording duration. Collect at least three samples per case before comparing medians. A faster warm retry in unchanged code is not an optimization result. Model preparation moved before the session tap must also be counted in launch-to-ready measurements.

## Instrumented baseline

Build 3 adds `SpeechPerf` records without changing the model-loading or inference algorithm. Native session records carry an operation ID, build number, stage, and monotonic elapsed milliseconds. Stages cover request, microphone permission, model readiness, audio activation, audio-engine start, listener readiness, and final session readiness. Model and transcription records measure their full native calls. Keyboard records correlate start, stop, cancel, and insertion completion with the utterance request ID. No recording paths, transcripts, audio, endpoints, keys, or session secrets are logged.

## First experiment

Build 4 keeps the v3 INT8 weights and the encoder on CPU plus Neural Engine, while using CPU-only decoder/joint models. Both download-and-load and installed-model load use the same configuration. The pinned [FluidAudio loader](https://github.com/FluidInference/FluidAudio/blob/v0.15.5/Sources/FluidAudio/ASR/Parakeet/SlidingWindow/TDT/AsrModels.swift) exposes this placement through `configuration` and `encoderComputeUnits`. The hypothesis is that smaller autoregressive networks spend more time dispatching than computing on the Neural Engine. Keep this only if physical measurements improve and transcription still works correctly in the background. No GPU execution is introduced.

Build 4 was installed and confirmed over USB. Capture PID `38432` was stopped after the maintainer completed the attempt. The trace contains one session, two keyboard utterances, and one native transcription without keyboard insertion, consistent with the requested in-app attempt. It does not contain the requested second cold launch or same-process restarts.

The keyboard native inference durations were 254.228 and 187.117 ms, compared with the first process's build 3 samples of 260.655 and 191.447 ms. Stop-to-insertion took 251.336 and 189.536 ms. This does not establish a useful gain beyond the observed variation. The additional in-app native transcription took 168.495 ms, but there is no corresponding in-app baseline or full Stop-to-UI timing. The first post-install session took 19,693.665 ms, including 18,417.789 ms of model loading; one compilation trial per build cannot establish a compilation improvement.

The CPU-only decoder/joint placement was rejected and reverted.

## Second experiment

Build 5 tests retaining the audio tap while the engine is stopped between sessions, using the input's native format. The engine still stops, the temporary utterance is discarded, and the audio session deactivates at session end. The tap writes nothing without an active utterance file. Failed starts remove the tap and clear its installed flag so a later retry can rebuild it. Additional timing points split category setup, input-format setup, tap installation, and engine start.

Build 5 was installed and verified over USB. Capture PID `107308` was stopped after the attempt. Same-process session restarts took 289.350 and 276.283 ms, a median of 282.817 ms against build 3's 297.547 ms. The approximately 5% difference fails the one-third target of 198.365 ms. Input-format lookup and the retained-tap step took under 1 ms combined, while audio activation and engine start still took roughly 121–128 ms and 132–134 ms respectively. The extra retained-tap state was rejected and reverted. The first session after installation took 35.727 seconds, including 35.139 seconds of model loading; this reinforces the need to keep compilation cases separate.

## Build 6 phone check

The [build 6 Release build](https://expo.dev/accounts/parthashirolkar/projects/shuddhalekhan-mobile/builds/2d37a2b8-77f8-4fc0-b554-34bf288d63f7) finished successfully after the maintainer authorized it. The [build 6 IPA](https://expo.dev/artifacts/eas/FmK9jatWuQhVeTGkCyXGJywKOFfBXxIvoxXJ9ShWigY.ipa) was installed and verified over USB before the trial below. Both the CPU-only decoder and retained-tap experiments have been removed from source. The original model configuration and session teardown are restored.

Changes included in build 6:

- Preload an installed model after saved settings load, only when on-device transcription is selected. It uses the existing native `prepare()` and shared load task. Preparation never downloads models or starts the microphone; explicit session/transcription requests still retry and report their own errors if speculative preparation fails. Home shows preparation progress and Settings calls the disk state "Model installed".
- Remove duplicate command acknowledgements. Build 3's four utterances each received two recording and two transcribing states. The server now uses the state already published by a synchronous transition, replying separately only when a command leaves state unchanged. The native transport check asserts exactly one recording and transcribing acknowledgement before the final frame, without sleeps. The updated check passed in build 6.
- Stabilize the custom keyboard header and action row. Reserve two lines for status, distribute spare height evenly over the letter rows, keep Cancel present but disabled at rest, and avoid a required height constraint competing with iOS during appearance. Show one timer at a time, with full session/recording timing available to VoiceOver. There is no Dynamic Type cap.
- Use UIKit button configurations for immediate key, Dictate/Stop, and Cancel highlighting. Opening/TCP connection timing logs were added. No polling or animation loop was added.
- Simplify Home during an active keyboard session by prioritizing the session card and hiding the disabled in-app recorder and irrelevant idle status. Keep required setup and security information available in Settings.

The latest JavaScript changes pass mobile typecheck, lint, and the 15 focused controller/settings/storage tests. The build 6 cloud Mac compiled the Swift changes, bundled the JavaScript, passed both native protocol/transport checks, and produced a successful Release archive. This does not establish phone performance or visual behavior.

Remaining checks include repeated process-cold and same-process samples, launch-to-ready timing, endpoint-only startup, error layouts, larger accessibility text, interruption/expiry, and a second host app. The available phone results below do not cover that full matrix.

Build 6 was verified installed on the same iPhone over USB before capture PID `145436` started. It was stopped after the maintainer completed the trial. One session request-to-ready duration was captured at 298.397 ms, with model readiness reached in 2.224 ms after the request. The model-load completion record appears immediately before the request and reports 537.093 ms of preparation. This confirms that preparation occurred before the session tap on this trial, but does not measure total app launch-to-ready time. The trace does not establish a repeated-session median. Compared with the single build 3 prepared process-cold sample of 396.534 ms, the captured tap-to-ready reduction is approximately 25%, short of one third, with insufficient trials for a stable comparison.

Both captured utterances received one recording acknowledgement and one transcribing acknowledgement, compared with two of each in all four build 3 utterances. The maintainer confirmed that the dictation panel no longer wobbles and clarified that the remaining keyboard issue was the missing enlarged character-key preview. The native server regression check had already passed in the build 6 cloud build.

## Build 7 character previews

Build 7 adds one reusable, noninteractive character preview above the pressed key. It follows the current letter case and supports digits/symbols. It dismisses on release, drag-out, cancellation, keyboard hiding, row rebuild, and case changes. Only the current key owns dismissal, preserving two-finger interaction. Insertion stays on the existing touch-up-inside path. The preview is clamped inside the keyboard view, as required by the [custom keyboard drawing boundary](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/CustomKeyboard.html). It adds no timer, animation loop, logging of keys, or keyboard-height changes. A debug assertion checks the drawing boundary.

The [build 7 Release build](https://expo.dev/accounts/parthashirolkar/projects/shuddhalekhan-mobile/builds/a45cbfdc-67b2-45c8-be53-b0d86d18e61e) succeeded. The [build 7 IPA](https://expo.dev/artifacts/eas/vrdklTkt1QTxmPFNOt1K7yX-Im2bCaD-CbDjRr6uxbg.ipa) includes the character preview. The startup path is unchanged from build 6. The maintainer installed it and confirmed that the preview works. No new USB capture or detailed case-by-case results were collected for build 7. Edge keys, case/symbol changes, drag-out/cancellation, fast typing, and exactly-once insertion still need an explicit full-matrix check.

The one-third startup target is not met. Raw captures remain local and all capture PIDs started in this task have been stopped.
